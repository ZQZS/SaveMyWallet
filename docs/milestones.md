### 2026-11-21 明细与整笔分期的作废和恢复

本次开发沿用应用版本 0.3.0。录错的账单可以在月度清单中作废，原明细仍可查阅，金额从所属月份的应还和预算汇总中扣除。分期可从任意一期选择仅处理本期或处理整笔。确认前会显示起止月份、受影响期数和其中已还的期数。恢复后，每期按原金额和原还款状态重新计入。[使用说明](../frontend/README.md#使用)

新分期的各期共享一个 `installmentId`，每期仍有独立的明细 ID。旧分期按平台、名称、每期金额、总期数和首月匹配。各期完整且唯一时可整笔操作，缺期或有歧义时可逐期处理。SQLite v5 保存分期标识，含该标识的 JSON 备份使用 v3，新客户端兼容 v1 至 v3 备份。跨设备使用新分期前需更新服务端和各客户端。[迁移与同步协议](../backend/docs/sync.md) · [备份回归用例](../frontend/src-tauri/src/ledger/tests/backup.rs)

### 2026-11-21 预计补款的定金与应补金额

录入和确认预计补款时可填写总价与已支付定金，月度清单和结余只计入应补金额。定金默认 0 元，旧账单沿用原金额。总价 100 元、定金 20 元的款项只计入 80 元。已全额预付的款项确认后直接结清。SQLite v6 保留原有明细 ID，含非零定金的账本以 v4 格式备份。[使用说明](../frontend/README.md#使用) · [本地迁移](../frontend/src-tauri/src/schema_v6.sql)

Windows 客户端已验证旧账本升级、总价调整后保留定金、重启和备份恢复。两份独立 SQLite 账本与 PostgreSQL 的同步验证也已通过。两端分别把同一笔款项确认为总价 100 元、定金 20 元和总价 110 元、定金 30 元时，即使双方应补均为 80 元，仍会产生冲突供用户核对。选择保留的版本后，两端与服务器的金额一致。[双副本验证](../frontend/src-tauri/src/sync_client/live_tests.rs)

## 客户端里程碑与验收

DeepSeek 助手覆盖月度解释、截图录入、分期试算、尾款通知对账和一句话查账。后两项的验收场景如下。M1 已接入三个应用内桌宠与酒馆角色卡导入。M4 的桌宠聊天使用本机 DeepSeek Key，真实 API 回复和 Android 真机体验仍待验。M5 独立桌面窗口仍在规划。[桌宠与角色卡](../frontend/docs/pets.md) · [助手使用与验证](../frontend/docs/ai-features.md)

- **尾款通知对账**。已有总价 100 元、定金 20 元的预订，收到「下月补 100 元」的通知。核对新月份、总价 120 元、定金 20 元和应补增加 20 元。确认后原 ID 保留，同名其他记录完整。取消后原账本保持原值。
- **一句话查账**。用「下个月有哪些付过定金、还需要补款的订单？」提取条件，在本机找出符合条件的有效明细。核对预计补款与已确认待还的合计，已作废和应补为零的订单应从这次结果中排除。

这两项功能已在 Windows 客户端用独立 SQLite 账本和模拟的模型回复验收。一次对账将原单尾款从 468 元调至 498 元，保留 52 元定金，其余四条明细保持原值。双击确认、写后读取失败并重试，重启后仍只有一笔更新。桌面和 360 像素宽的浏览器中，组合查账返回两笔，待确认 75 元和已确认待还 40 元，合计 115 元，均能点回原明细。

2026-11-21 在 Windows 客户端用隔离账本和测试凭据验证了密钥保存、更换与删除。将每期 32.50 元、共 6 期的试算转为正式账单后，SQLite 中同一笔分期恰有 6 条明细。桌面和 360 像素浏览器布局用模拟识别结果验证了逐笔审核、取消、重复点击确认及写后刷新失败重试。本地 HTTP 测试覆盖截图请求编码、返回草稿和服务错误。Android arm64 调试 APK 已通过构建与签名校验。[HTTP 测试](../frontend/src-tauri/src/ai/deepseek/transport_tests.rs)
